# Полный цикл разработки

Ведёт цикл от собранного файла (`docs/cycles/cycle-N.md`, его создал `cycle-start`) до слияния в `main`. Работает **фазами по всем пунктам сразу**, а не прогоняет каждый пункт отдельным конвейером. Грязную работу раздаёт субагентам (`.claude/agents/`), сам — оркестратор: держит решения, группирует, мержит.

**Одна остановка на пользователя — макеты (гейт).** Все дизайн-вопросы пользователю — макетом, не словами: «как показать историю капитала», «где рисовать график», «куда убрать ленту» — это дизайн, его решает `designer` вариантами в HTML-артефакте, пользователь выбирает по картинке. Задавать такое текстом запрещено — на словах решить нельзя.

Текстом (`AskUserQuestion`) задаются **только** вопросы, которые макетом не решить и которые реально блокируют: источник данных (откуда брать поле, которого нет в домене), бизнес-правило без ответа в ТЗ/коде, выбор между двумя путями, где оба меняют поведение (не вид). Пусто таких — текстовый гейт пропускается, идём сразу к макетам. «Уточни тон/подпись/формулировку» — не вопрос, решай сам в стиле «Слитка».

После гейта макетов — автономно до `main`; останавливает только красный CI (чинится сам). `device-check` (Фаза 6) — тоже автономно: раз нужен, запускай сам, разрешения на эмулятор не спрашивать.

## Экономия токенов (обязательно)
Главный расход — входной (перечитывание файлов субагентами). Держи его низким:
- **Контекст вниз, не заново.** `explorer` один раз строит карту кода; сохрани её в `docs/cycles/cycle-N-map.md` и вкладывай путь к ней в задания `architect`, `coder`, `tester` вместе с планом. Они читают карту и названные `file:line`, а не сканируют репозиторий.
- **Right-size конвейера по размеру пункта** (см. Фазу 0): на тривиальное не зови `architect`(opus) и `reviewer`.
- **Тёплые правки.** Замечание по работе — тому же агенту через `SendMessage` (контекст горячий), не новому холодному.
- **Ревью волной.** Один `reviewer` на весь диф волны, не по агенту на каждую группу.
- **Низкий effort механическим агентам** (`coder` по плану, `explorer`, `device-check`): ставь `effort: low` в вызове `Agent`; `architect`/`designer` — обычный (там суждение).
- **Короткие хэндбэки.** Агенты и так настроены отвечать сжато; не пересказывай их простыни в своём окне.
- **Поменьше тяжёлых opus-агентов разом** — иначе упираешься в лимит сессии (429) и платишь за переспавн дважды.

## Два уровня правил (помни на всех фазах)
- **Инварианты** — не нарушаются никогда, даже при редизайне: слои DDD (`ui → domain ← data`), деньги в копейках (`Money`), домен без Android, приватность (не SMS, не `QUERY_ALL_PACKAGES`), стабильная подпись, офлайн/локально, зелёные тесты, цвет/шрифт через токены `ui/theme` (не хардкодом). Часть стоит хуком `.claude/hooks/guard.ps1`.
- **Текущие решения дизайна** — число вкладок (сейчас 4), палитра, набор экранов. Это сегодняшний вид, его редизайн меняет (с согласования).

## Фаза 0. Классификация пунктов
Прочитай `docs/cycles/cycle-N.md`. Каждый пункт отнеси к классу:
- **Рядовой** — баг, мелкая доработка, фича в рамках текущего дизайна. Едет автономным групповым конвейером.
- **Дизайн/структурный** — «проанализируй/предложи дизайн», новая навигация, смена решения, смежного с инвариантом (напр. число вкладок), перестройка. Только **предложение**: доходит до макета-гейта и ждёт пользователя, **не** мержится автономно. Если рядовой пункт по ходу анализа требует смены инвариант-смежного решения — переквалифицируй его в этот класс.

И по **размеру** — он задаёт глубину конвейера (экономия токенов):
- **Тривиальный** (1–2 файла, механика: строка, переименование, мелкая правка) — оркестратор даёт `coder` короткий бриф напрямую, **без** `architect` и `reviewer`.
- **Средний** — `architect` с `model: sonnet` + `coder` (+ `reviewer` в волне).
- **Тяжёлый / дизайн-смежный** — `architect` на `opus` + `reviewer`.

## Фаза 1. Анализ (все пункты)
- `explorer` — карта по коду: где что, какие файлы и экраны трогает каждый пункт (нужно для группировки). Сохрани его карту в `docs/cycles/cycle-N-map.md` — дальше все агенты читают её, а не ищут заново.
- `architect` — план каждого рядового пункта по слоям DDD, со списком файлов и проверяемыми критериями. Дай ему путь `docs/cycles/cycle-N-plans.md` — план пишет туда сам (своим разделом `## <ID>`), текстом в ответ не возвращает; это экономит токены на пересказ через оркестратора.
- `designer` — по дизайн/структурным пунктам: анализ и варианты (пока без кода).
- **Не один опус-агент на пункт.** Независимые пункты (без общих файлов, без общего решения) планируй **одним вызовом** `architect`/`designer` на несколько пунктов разом (каждый пишет свой раздел `## <ID>` в тот же файл планов) — повторный системный промпт и чтение `CLAUDE.md`/карты на каждый пункт того не стоят. Отдельный вызов — только если пункты реально независимы по сути (разный объём контекста, разные решения) и параллелить дешевле, чем сериализовать в одном.
Запиши в файл цикла: статус пунктов `разобрано`, у каждого — список затрагиваемых файлов (читай из `cycle-N-plans.md`).

## Фаза 2. Блокирующие вопросы — опционально
Пройди по всем пунктам и выдели **только** реально блокирующие нон-дизайн вопросы (источник данных, бизнес-правило, выбор пути поведения). Дизайн-вопросы сюда **не** попадают — они идут в фазу 3 вариантами макетов. Нашлось такое — задай пакетом (`AskUserQuestion`), жди ответа. Не нашлось — пропусти фазу, иди на макеты.

## Фаза 3. Макеты — один пакет (гейт)
- `designer` рисует макеты по всем пунктам, где меняется вид (включая варианты дизайн/структурных и варианты ответа на дизайн-вопросы, которые раньше были бы текстом). Каждый пункт — HTML-артефакт через `Artifact` с вариантами колонками/табами (телефонный фрейм, токены «Слитка», состояния, жесты). Параллельно складывает исходники в `docs/mockups/cycle-N/`.
- Выдай пользователю ссылки на **все артефакты разом**, он выбирает вариант по каждому пункту. Жди «ок».
- Без «ок» ни один пункт с изменением вида дальше не идёт. Пункты без изменения вида этот гейт не держит.
- Комментарии к макету приходят в эту сессию — правь артефакт сама (`Edit` исходника + `Artifact` republish тем же `file_path`/`url`), `designer` заново не зови: resume субагента через `SendMessage` дороже (перезагрузка его контекста), чем мелкая правка макета прямо тут.

## Фаза 4. Разработка — группами, автономно

**Утверждённый макет — закон.** В задании кодеру всегда дай путь к утверждённому макету (`docs/mockups/cycle-N/<ID>/...html`) и явное требование: реализовать вид строго как на макете — состав строк, подстроки, счётчики, разделители, цвета, подписи. Расхождения (данных нет в домене, устроено иначе) — выносить обратно оркестратору, а не упрощать молча. После реализации — визуально сравнить скрин экрана с макетом; это задача `device-check`. Если видишь, что реализация отошла от макета без объяснения — круг правок у того же тёплого кодера.

Группируй рядовые пункты по пересечению файлов (из планов `architect`):
- Пункты с **общими файлами** → одна группа, кодятся последовательно (один `coder`), коммит на пункт (ID в сообщении, напр. `U-57`). Два писателя никогда не трогают одни файлы одновременно.
- **Непересекающиеся** группы → параллельно (отдельные `coder`, каждый в своём worktree).
- **В задание `coder` давай путь к разделу плана** (`docs/cycles/cycle-N-plans.md#<ID>`) **и путь к карте** (`docs/cycles/cycle-N-map.md`) — он читает файлы сам, не пересказывай план текстом (план уже на диске, не в твоём контексте — пересказ означает лишнее чтение файла тобой же). Тривиальному пункту `architect` не нужен — дай `coder` короткий бриф сам.
- Правки по замечаниям — **тому же `coder` через `SendMessage`** (тёплый контекст), не новому.
- `tester` — доменные тесты по TDD (падает без фикса, зелёный после) только там, где есть доменная логика.
- `reviewer` — **один на диф всей волны**, не по группе; тривиальные механические правки можно без `reviewer` (хук + тесты + `DesignSystemGuardTest` стерегут).
- Механических агентов (`coder`, `explorer`) зови с `effort: low`.
- Хуки стерегут инварианты; `coder` перед сдачей гонит `./gradlew testDebugUnitTest assembleDebug` до зелёного.

### Круг правок после ревью (с кэпом)
`reviewer` отдаёт находки с severity (`блокер`/`важное`/`мелочь`) и вердикт — сам не правит. Дальше решает оркестратор:
- `блокер`/`важное` → отдай находки **тому же `coder`** через `SendMessage` (тёплый контекст), он чинит.
- `мелочь` → отложи или собери партией; отдельный круг ради неё не гоняй.
- Пере-ревью — **только по дифу правки** (`git diff`), не весь код заново.
- **Кэп: максимум 2 круга правок на группу.** Не сошлось за 2 (остались блокеры) — стоп: пометь пункт «застрял», вынеси пользователю с находками, дальше не крути (бесконечная петля reviewer↔coder — самый дорогой сценарий).
- Выход круга: `reviewer` без блокеров/важного + зелёный `./gradlew testDebugUnitTest`.

## Фаза 5. CI — волнами
Пушь пачками (группа/волна), **не по пункту и не по коммиту**. Жди зелёный `build.yml`; красный — `gh run view --log-failed`, чини, пушь, пока не зелёно. Тесты не ослаблять.

## Фаза 6. Проверка на устройстве
Не спрашивай у пользователя, проводить ли — если по циклу она нужна, запускай `device-check` сама. `device-check` на эмуляторе: поставить debug-APK, снять экраны ключевых экранов затронутых пунктов, метрики кадров (`dumpsys gfxinfo` / Macrobenchmark). Что ловится числами/скринами — чинить в цикле. Тонкую визуалку (вспышка на кадр, плавность) агент по скринам не ловит — собери её в список «проверить на устройстве» для пользователя.

## Фаза 7. Слияние (скилл `release`)
Все рядовые пункты `готово` (или `отложено`/`отклонено` с причиной), CI на `cycle-N` зелёный → слить в `main`, запушить, дождаться зелёной сборки на `main`. Файл цикла остаётся в `docs/cycles/` архивом. Дизайн/структурные пункты, не одобренные на гейте 2, в этот цикл не входят — переносятся или ждут отдельного захода.

## Отчёт пользователю в конце
Что сделано по пунктам, что отложено/отклонено с причиной, список «проверить на устройстве», ссылки на зелёный CI.
