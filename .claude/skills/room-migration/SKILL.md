# Миграция схемы Room

Редкий процесс, вынесен из CLAUDE.md. С версии БД 10 данные пользователя реальны — **каждая смена схемы идёт с миграцией**, не с разрушением.

## Порядок
1. Открой `data/local/AppDatabase.kt` — посмотри текущий `version` в `@Database`.
2. Измени/добавь `*Entity` (и `*Dao`, `*Mappers` при нужде). Новую entity добавь в массив `entities` и `abstract fun dao()`.
3. **Подними `version` на 1.**
4. Напиши `Migration(старая, новая)` рядом с существующими (`MIGRATION_12_13` и т.п.): точный SQL (`ALTER TABLE ... ADD COLUMN`, `CREATE TABLE IF NOT EXISTS`, индексы). Значения по умолчанию для новых NOT NULL-колонок обязательны.
5. Зарегистрируй миграцию в `.addMigrations(...)` в `AppDatabase.get`.
6. Не ломай путь шифрования: открытие БД идёт через `SupportOpenHelperFactory` (SQLCipher) — оставь как есть.

## Чего не делать
- Не удаляй `fallbackToDestructiveMigration()` вслепую: он нужен для старых схем (< v10), но новые версии ДОЛЖНЫ иметь миграцию, иначе данные сотрутся.
- Инструменты — KSP, не kapt.
- Доменные модели неизменяемы; Room-аннотации в домен не тащи, маппинг — в `*Mappers`.

## Проверка
- Собери: `./gradlew assembleDebug` (KSP сгенерирует код, несоответствие схемы всплывёт).
- Проверь `./gradlew testDebugUnitTest`.
- На устройстве: обновление поверх старой версии с данными — данные на месте, приложение не падает при первом запуске.

## Если менял поля резервной копии
Новые поля, которые должны переживать переустановку, добавь и в `data/backup` (формат копии), как сделано для логотипов и отметок настроек.
