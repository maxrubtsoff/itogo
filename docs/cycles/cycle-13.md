## Пункты

### B-79. График: вклад появляется в дату добавления, а не в дату открытия
**Тип:** ошибка. **Приоритет:** P2. **Статус:** новое.

Вклад, добавленный сегодня с датой открытия 01.06.2026, попадает на график изменения капитала точкой «сегодня»; точки на 01.06.2026 нет. Ожидание: вклад отображается на графике с даты открытия — когда он добавлен в приложение, значения не имеет.

### B-80. Скрины вкладов распознаются не полностью
**Тип:** ошибка. **Приоритет:** P1. **Статус:** новое.

Загрузка скринов карточек вклада («Вклад №1: Альфа-Банк», завершён, 650 000 ₽ → 770 191,47 ₽, 18,49 %, 07.08.2024 — 07.08.2025) даёт неполный результат:
- в большинстве случаев не распознаётся сумма при открытии;
- местами не распознаются даты периода;
- название вклада распознаётся как «Сумма при открытии вклада» (подпись поля принята за название).

Скрины — разные вёрстки одной карточки: `docs/cycles/cycle-13-shots/B-80/deposit-1..5.jpg`:
1. светлая карточка, сетка в 3 колонки, подписи «Сумма на входе / Сумма на выходе / Ставка», даты строкой ниже, цветные суммы;
2. 4 колонки в одну строку, «Сумма при открытии вклада» переносится на две строки;
3. одна колонка, суммы без пробелов-разделителей (`650000₽`);
4. одна колонка, у суммы открытия **нет подписи**;
5. одна колонка, подпись просто «Сумма».

Ожидание: все поля (название/банк, сумма открытия, сумма в конце, ставка, даты, статус) распознаются на всех пяти. Проверка — прогнать эти скрины через распознавание на эмуляторе (`device-check`).

### B-81. Подписи значимых точек на графике толстые, с толстой обводкой
**Тип:** ошибка. **Приоритет:** P2. **Статус:** новое.

Подписи сумм у значимых точек на графике изменения капитала (появились в F-49, цикл 12) по-прежнему выглядят толстыми и с толстой обводкой — «до сих пор», то есть уже замечалось. Ожидание: тонкий аккуратный текст по «Слитку», без грубого контура. Проверить на всех вкладках обзора, где есть такие подписи, и снять скрин на эмуляторе (`device-check`).

### F-51. Доступ к операциям истории: просмотр, правка, удаление, переход к уведомлению
**Тип:** хотелка, дизайн-пункт (нужны макеты). **Приоритет:** P1. **Статус:** новое.

Сейчас с операцией из истории ничего нельзя сделать — ни посмотреть подробно, ни исправить, ни удалить. Из-за этого мусор попадает на график и в капитал.

Примеры:
- **Наличные.** «Ради прикола» изменил сумму: взял 1000, вернул 1000 — на графике два изменения, хотя по сути ничего не было. Нужна возможность удалить такие изменения. Тап по операции наличных сейчас просто переводит в раздел «Наличные» — бесполезно, нужно показывать саму операцию.
- **Счета.** В истории есть операция +20,26 млн — такой не может быть (ошибка распознавания). Ни отредактировать, ни удалить, ни перейти к ней нельзя.

Хотелось бы:
- для операций по счёту — открывать снизу шторку с просмотром операции и там же править/удалять;
- из операции переходить к **уведомлению, которое её породило** (журнал);
- для остальных видов (вклады, наличные, валюта и пр.) — продумать, нужна ли та же шторка или другое поведение; для наличных — точно показывать саму операцию, а не раздел.

Учесть: после правки/удаления пересчитываются баланс, график и капитал. Связано с F-36 цикла 11 (тап по строке истории открывает объект) — это поведение пересматривается.

### U-67. Удержание на графике: операции подтягиваются сразу, график стоит на месте
**Тип:** удобство. **Приоритет:** P2. **Статус:** новое.

Сейчас при нажатии и удержании на графике (выбор точки) список операций ниже прокручивается к нужным операциям только **после отпускания** пальца — экран уезжает вниз.

Ожидание:
- прокрутка списка происходит **сразу**, пока палец ведёт по графику;
- экран не опускается к операциям — нужные операции **подтягиваются вверх**, под график;
- график изменений остаётся в поле видимости и **на месте** и при нажатии, и при отпускании пальца.

Проверить на эмуляторе (`device-check`): ведение пальцем по графику, отпускание, без скачков экрана.

### B-82. Парсер берёт голое длинное число за сумму
**Тип:** ошибка. **Приоритет:** P1. **Статус:** новое.

`domain/parser/NotificationParser.kt:160-161, 192-198` (MASK 73-76). Если до слова баланса нет числа с валютой, `plainAmount` берёт первое голое число (до 15 цифр): номер счёта, ID, дату-референс. Примеры: «Перевод от Иван И. Счёт 40817810 Баланс 5 000 ₽» → +40 817 810 ₽; 8-значный `2026xxxx` → +20,26 млн; «Карта ·· 2026» → +2026 ₽ (MASK не знает `··`, «Счёт 4081…» с пробелом, `ECMC2026`/`MC`/`MAES`). Вероятная причина операции +20,26 млн (см. F-51). Ожидание: по правилу консервативности — без валютного маркера суммы нет, `null`.

### B-83. «+7» телефона задаёт направление и сумму
**Тип:** ошибка. **Приоритет:** P1. **Статус:** новое.

`NotificationParser.kt:103, 225-227`. Без слова направления `SIGNED_AMOUNT` ловит «+7» номера телефона. «Перевод по номеру +7 926 263-45-67 1 500 ₽» → доход; «Перевод от +79262634567» → 792 626 345,67 ₽.

### B-84. Входящий перевод с именем отправителя пишется как расход
**Тип:** ошибка. **Приоритет:** P1. **Статус:** новое.

`NotificationParser.kt:229` (IN_MARKS 94-97). «входящий» не входит в признаки дохода, «перевод от» ловится только подряд; срабатывает запасное «TRANSFER + контрагент ⇒ OUT». «Входящий перевод 500 ₽ от Ивана Иванова» → −500.

### B-85. Вклад или валюта задним числом дают ложные «Проценты»/«Переоценку»
**Тип:** ошибка. **Приоритет:** P1. **Статус:** новое.

`domain/model/CapitalEvents.kt:242-246, 268-269`. Взнос считается вложением, только если дата вклада/пополнения/сделки равна дате точки. Сегодня добавлен вклад на 1 000 000, открытый месяц назад → в истории «Проценты +1 000 000+»; покупка $1 000 недельной давности → «Переоценка» на всю рублёвую сумму. Связано с B-79, но это отдельный дефект.

### B-86. Операции валютного счёта показаны в рублях и дважды
**Тип:** ошибка. **Приоритет:** P1. **Статус:** новое.

`CapitalEvents.kt:165-176`, отрисовка `ui/common/HistoryLine.kt:102`. Сумма в минорных единицах валюты кладётся в `amountMinor` и рисуется с ₽, без пересчёта и без `foreign`. Платёж 20 263 000 UZS → «−20,26 млн ₽». То же изменение баланса ещё раз приходит через `moved()` как «Переоценка… Остаток изменили вручную». Группы складывают разные валюты. Вторая возможная причина +20,26 млн.

### B-87. Привязка нового приложения к известному банку не сохраняет пакет

### B-90. Починка из журнала оставляет ложный баланс

### B-91. Сбой Keystore стирает зашифрованную базу
**Тип:** ошибка. **Приоритет:** P1 (по последствиям; уверенность средняя). **Статус:** новое.

`data/local/AppDatabase.kt:128-133`, `data/local/DatabaseCipher.kt:96-106`, `data/security/PhoneKeys.kt:30-41`. Любое исключение даёт пустой пароль → зашифрованный файл удаляется; если `getKey` вернул null — генерится новый ключ, старый секрет не открывается, файл удаляется. Сбой Keystore после обновления ОС → все данные потеряны, а следующее изменение перезаписывает сегодняшнюю автокопию пустыми данными. Ожидание: при сбое ключа — не удалять, а показать ошибку/предложить восстановление; автокопию пустой базой не перетирать.

## Решения гейта (2026-10-26)

- **F-51** — вариант A: шторка операции (просмотр, «Изменить» превращает её в форму, удаление с цифрами «было → станет» и снекбаром «Вернуть»). Поведение по видам операций из вкладки макета — утверждено. Уведомление банка видно сразу при открытии шторки, переход в журнал — стрелкой «›», без надписи. Пересматривает F-44 и F-50.
- **U-67** — вариант B: при прокрутке герой сжимается в полосу 64 dp и прилипает под шапкой, по полосе тоже можно вести пальцем; во время ведения двигается только список. Дополнительно: смена дня в списке идёт **плавной анимацией** — операции подъезжают аккуратно и быстро, не появляются рывком. Нужна проверка на устройстве (`device-check`).
- **B-91** — чиним причину, а не следствие: не создавать новый ключ поверх существующей запечатанной фразы, не выдумывать фразу при существующем файле базы, отличать временный сбой Keystore от настоящей потери, файл базы не удалять никогда. Страховка: если задан пароль копии, запечатывать фразу ещё и им. Экран ошибки — последний рубеж, без слов «ключ» и «Keystore».
- **B-101** — ответ ждём; по умолчанию вариант А+ (итог дня по сегодняшнему составу, дни с выключенным разделом досчитываются один раз), ступенька от исключённых счетов в этом цикле остаётся.
